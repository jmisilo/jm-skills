How a GPU works

A GPU, or graphics processing unit, is a chip built to run thousands of threads in parallel, giving up single-thread speed to get far more total work done per second.1 It began as the part of a computer that draws images, and the same design is now used to train and run AI models.10

A CPU is built to finish one sequence of instructions as fast as possible, so it spends many of its transistors on caches, small fast memories that keep recent data close, and on control logic.1 Drawing a frame or multiplying two large matrices, grids of numbers, is a different problem: the same few steps repeated over millions of independent items, where no single item has to finish early. A GPU spends its transistors on arithmetic instead.1 An H100, NVIDIA's datacenter GPU, holds up to 2,048 threads in each of its 132 cores, over 250,000 at once.4

Work arrives from the CPU over PCI Express (PCIe), the link between the motherboard and the card, and a front end on the GPU reads the commands.5 It hands blocks of threads to the GPU's cores, which NVIDIA calls streaming multiprocessors, or SMs. The SMs share one large cache, the L2, and the GPU's own memory, VRAM, a set of memory chips on the card that the cache reads at 3 terabytes per second (TB/s).110 The steps below follow work down that path.

Before you start

00
Kernel
The program a GPU runs. It is written as if for one thread and launched over a grid of thousands or millions of threads.1
Thread
One run of the kernel on one piece of data. Each thread keeps its variables in registers, the small private storage slots right beside the math units.1
Warp
A group of 32 threads that the hardware schedules and runs together, one instruction for all 32 at a time.1
SM
Streaming multiprocessor: one of the GPU's cores, with its own schedulers, registers and math units. Each is much weaker than a CPU core; there are many of them.4
Latency, throughput
Latency is how long one operation takes; throughput is how many finish per second. CPUs are built for the first, GPUs for the second.1
Bandwidth
How many bytes per second memory can deliver. A program that does little math per byte it reads runs at the speed of its bandwidth, not of its arithmetic.8

The CPU queues commands, the GPU reads them

01

A program never runs code on the GPU directly. It calls a graphics or compute library, and the driver turns each call into hardware commands written into a command buffer in memory.5 The driver then updates a counter on the GPU that marks where the new commands end, and the GPU's front end, the command processor, fetches the new commands across PCIe and starts the work.5 Input data crosses the same link, copied from the CPU's RAM into VRAM before the kernel runs.2

The GPU is a separate processor with its own memory, so the two sides talk through a queue rather than by calling each other. Drivers run ahead on purpose: a graphics driver can be up to three frames ahead of the GPU, so the GPU always has work waiting.5 The CPU returns from a launch at once and prepares the next batch.

The link is the narrow part. PCIe version 5 moves 64 GB/s each way, against 3,000 GB/s between an H100 and its own memory, so the link is about 47 times slower (3,000 / 64).3 NVIDIA's own guide ranks cutting these transfers as a top priority, even if that means running steps on the GPU that are no faster there.2 A program that copies data over for one small calculation, or waits for each result before sending the next command, spends its time on the bus and in the queue rather than computing.

A grid of blocks spreads across the SMs

02

A kernel launch names a grid: how many blocks of threads, and how many threads in each block.1 The front end hands whole blocks to SMs that have room, and inside the SM each block is cut into warps of 32.1 A grid can hold millions of blocks while the GPU has tens or hundreds of SMs, so most blocks wait their turn.1

The rule that makes this work is that blocks do not depend on each other: the programming model requires that they can run in any order, side by side or one after another.1 That is why the same program runs on a GPU with one SM or thousands; a bigger GPU just works through the queue faster.1 Threads inside one block can cooperate through shared memory, a scratchpad on their SM that only that block's threads can see.1

Too few blocks leaves SMs idle: a grid of 100 blocks on a 132-SM H100 can use at most 100 SMs, 76% of the chip (100 / 132).3 The last round matters too: with one block per SM, 133 equal blocks take two full rounds, and in the second one SM works while 131 wait. And because there is no guarantee about when other blocks run, a block cannot wait on another block's results mid-kernel.1

An SM spends its area on math lanes

03

An H100 SM has 128 FP32 lanes, units that each do one operation on a 32-bit decimal number per clock, and four warp schedulers.34 A clock is one tick of the chip's timing signal, about a nanosecond.4 So the SM works as four quarters: each scheduler issues one instruction for one warp per clock to its 32 lanes (128 / 4).4 The SM also holds a 256 KB register file, the bank that holds every thread's registers, 256 KB of fast memory that serves as its own cache and as shared memory, and four tensor cores, matrix units that step 8 covers.3

A CPU core spends much of its area on caches and on control logic that predicts branches and reorders instructions, so that one thread runs fast.1 An SM keeps little of that. A warp runs its instructions in order, and when it stalls the SM does not try to work around the stall; it runs a different warp. The saved area goes to math lanes and to a register file big enough to hold every resident thread's variables at once, 65,536 registers of 4 bytes (256 KB / 4 B).3 The bet is that many weak cores beat a few strong ones whenever the work splits into many independent pieces.1

The bet loses on serial work. One thread on an SM is far slower than on a CPU core, so code that cannot be split, such as following a linked list or parsing a file one character at a time, belongs on the CPU. The register file also caps how many threads fit: 65,536 registers over 2,048 threads is 32 registers each (65,536 / 2,048).34 A kernel that needs more per thread fits fewer threads on each SM, and step 5 shows why fewer threads means slower.2

A warp runs 32 threads in lockstep

04

NVIDIA calls the model SIMT, single instruction, multiple threads. Each SM creates, schedules and runs threads in warps of 32, and the 32 threads of a warp carry out each instruction together, each on its own data in its own registers.1 To the programmer every thread still looks independent: it has its own variables and can take its own branches.1

Fetching, decoding and scheduling an instruction costs area and power, and sharing that cost across 32 lanes is what lets an SM afford so many lanes. The work usually fits the shape: neighbouring pixels of one triangle run the same small program on similar data, and GPUs shade pixels in groups of 16 to 64 for exactly that reason.5

It breaks when threads of one warp disagree at a branch. The warp then runs each path that any of its threads took, one after the other, with the threads not on that path switched off.1 NVIDIA's guide warns that this divergence can significantly cut throughput, because it adds to the instructions the warp must execute.2 An if and else split 16 and 16 runs both halves at half the lanes; a branch with 32 different outcomes can run 32 times slower. Programs avoid it by arranging the data so whole warps take the same path.

The scheduler hides waiting by switching warps

05

Reading from VRAM takes hundreds of clock cycles, while an arithmetic instruction takes about 4.2 A CPU fights that delay with large caches that keep data close.4 An SM does something simpler: on every clock, each warp scheduler picks one of its warps whose next instruction has its inputs ready, and issues that.1 A warp waiting on memory is simply not picked.

Switching costs nothing because nothing moves. Every resident warp's registers and position in the program stay on the chip for the warp's whole life, so the scheduler can change warps from one clock to the next without saving or restoring anything.1 A CPU thread switch takes a few hundred to a few thousand cycles.4 This is what the huge register file pays for: up to 64 warps per SM, 16 per scheduler (64 / 4), all ready to run on any clock.4

The trick needs enough warps. With 16 warps per scheduler, some warp is almost always ready; cut that to a few, because each thread uses too many registers or each block too much shared memory, and all of them can be waiting at once while the lanes idle. NVIDIA calls the share of possible warps that are actually resident occupancy, and notes that low occupancy always hurts the ability to hide memory latency.2 More is not always better: once the waiting is covered, extra warps add nothing.

Memory is wide, far away and usually the limit

06

Memory is a ladder from small and fast to large and slow. Registers sit beside the lanes; each SM has 256 KB of L1 and shared memory; all SMs share a 50 MB L2 cache; and behind that sits 80 GB of HBM3, high-bandwidth memory, delivering 3 TB/s.3 HBM gets that speed from width: each stack of memory chips has a 1,024-bit interface and sits beside the GPU on an interposer, a silicon base that carries far more wires than a circuit board can.9

The width is there because the lanes eat data so fast. When a warp loads, the hardware merges its 32 threads' requests into as few memory transactions as possible, so 32 neighbouring 4-byte reads become one 128-byte fetch (32 × 4).2 The interposer is costly, because silicon is far more expensive to make than a circuit board.9

Many programs hit the memory limit before the math limit. The roofline model says it in one line: a program's best speed is the lower of peak arithmetic and bandwidth times its arithmetic intensity, the operations it does per byte it moves.8 An H100 does 60 trillion FP32 operations per second (60 TFLOPS) against 3 TB/s, so a kernel needs 20 operations per byte (60 / 3) to keep the lanes busy.38 Adding two arrays does one addition per 12 bytes moved, 0.083 per byte, and reaches 0.25 TFLOPS (3 × 0.083), under half a percent of peak.38 Scattered access makes it worse: reading every second number wastes half of each fetch.2

Drawing a frame mixes programs and fixed hardware

07

For graphics the same SMs run shaders, small programs written for one vertex or one pixel, and fixed-function hardware does the steps that never change.65 A vertex shader places each triangle's corners, its vertices, on the screen.5 The rasterizer, a fixed block of logic, then works out which pixels each triangle covers: first it tests 8 × 8 pixel tiles, then the pixels inside the tiles that might be hit, and it hands them on in 2 × 2 groups.5 Pixel shaders on the SMs compute each pixel's colour, and output units at the end blend it into the frame and test its depth, whether something nearer already covers that pixel.5

Older GPUs had separate vertex and pixel units, and one set sat idle whenever a scene leaned on the other. Unified shaders let any SM run any stage, so the load balances itself.6 The stages that stay fixed are simple and run for every pixel: testing coverage is a few integer additions and sign checks, done in parallel.5 Even so, designers keep fixed blocks lean, because they want the chip area and power in the shader lanes.5

Fixed hardware is fast at one job only. Because the rasterizer emits 2 × 2 groups, a triangle one pixel across still costs a group of four, so scenes made of tiny triangles waste most of the pixel work. Blending reads, changes and writes memory, and it must happen in the order the program drew things, so the output units have to sort overlapping pixels first.5 Layers of transparent smoke or glass pay that cost once per layer.

Tensor cores do matrix math in tiles

08

A tensor core is a unit that multiplies small matrices in one instruction. On the V100, where they first appeared, each one computes D = A × B + C on 4 × 4 tiles every clock: 64 multiply-adds, with 16-bit inputs and 16- or 32-bit results.7 The H100 has four per SM, 528 in all.3

Neural networks are built from matrix multiplications and convolutions, sliding-window filters, which is exactly what tensor cores speed up.7 In a matrix product each number is reused many times, so a unit that works on a whole tile at once does 64 multiply-adds per instruction instead of one, with no extra scheduling. The payoff is large: an H100 does 60 TFLOPS on its FP32 lanes and 1,000 TFLOPS of 16-bit math on its tensor cores, about 16 times as much (1,000 / 60).3

Tensor cores help only work shaped like a matrix product at the precisions they support; code that branches per element or needs 64-bit precision gets none of that speed. Feeding them is the second limit. At 1,000 TFLOPS against 3 TB/s, a kernel needs about 333 operations per byte (1,000 / 3) to reach the tensor roof in FIG. 8, so only large matrices, kept in shared memory and registers between uses, get near it.38

What it comes down to

09

A GPU is a bet that the work splits into many independent pieces. It spends its transistors on math lanes and registers instead of on making one thread fast, and it hides waiting by keeping thousands of threads on the chip and switching between them every clock.14 Every part on this page serves that bet, from the queue that keeps the GPU fed to the tensor cores that make its commonest job cheaper.

Two ideas carry over to other systems. Hiding latency with many waiting tasks, rather than shortening each wait, is also how a web server with thousands of open connections stays busy while each one waits on a database. And the roofline question, how many operations per byte moved, predicts the speed of any machine whose memory is slower than its arithmetic.8 To judge whether a job suits a GPU, ask it in order:

  1. Does it split? Thousands of independent items, with no item waiting on another's result.1
  2. Can the data stay on the card? PCIe is about 47 times slower than VRAM.3
  3. Do neighbouring threads agree? Same branch, neighbouring addresses, so warps stay whole and loads merge.2
  4. How many operations per byte? Under about 20 on an H100, memory sets the speed; matrix work at hundreds can use the tensor cores.38
  5. Is there room for warps? Few registers per thread, so the scheduler has warps to switch to.2

Going deeper. Consumer and datacenter GPUs share this design and differ in where they spend. A consumer RTX 4090 pairs 16,384 FP32 lanes with 24 GB of GDDR6X on a 384-bit bus, adds ray-tracing cores for lighting, and draws 450 W.11 A datacenter H100 carries 80 GB of HBM3 at 3 TB/s, 900 GB/s links to other GPUs, and draws 700 W.3 Integrated GPUs in laptops and phones have no VRAM of their own and share the CPU's RAM.10 The numbers that matter in practice are memory bandwidth, memory size, and peak operations per second at the precision you use; the ratio of the first and third says which wall a program hits.8 Read NVIDIA's CUDA Programming Guide next for the compute side,1 and Fabian Giesen's trip through the graphics pipeline for the drawing side.5

Limits. This page uses NVIDIA's names and the H100's numbers. AMD and Apple build GPUs on the same principles under other names, and their group sizes and memory layouts differ. Ray-tracing cores, video encoders, display output, links between GPUs and the shader compiler are left out. The costs of divergence, of the last round of blocks and of tiny triangles are worked examples, not measurements, and memory latency is given as hundreds of cycles because NVIDIA's guide gives no single figure.2
